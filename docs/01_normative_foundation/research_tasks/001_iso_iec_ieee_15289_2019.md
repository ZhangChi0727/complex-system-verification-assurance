## Research orientation

执行本任务前必须先读取本节与 frontmatter dependencies，并带着明确的研究问题、候选反证路径和来源边界进入原文。任务不是一般性总结，也不是为当前框架寻找支持。

### Task purpose and research attitude

确定生命周期信息项的 purpose、required content、过程关系和 conformance 边界，并检验这些内容能在多大程度上支持 VAF 概念信息架构而不被误写为 executable schema。

本任务服务于 `research_scope.md` 的三层目标：产品无关 Verification Methodology -> Model-Based Verification Architecture -> 非产品化 Verification Platform 研究原型。标准明确规定的内容形成构建约束；标准没有回答的内容形成 gap 或 innovation-space observation。`Standard wins over current framework hypothesis`；标准沉默不得由 agent 补齐，也不得作为 novelty proof。

### Source-specific research entry

原文目录显示研究总体包括 Clause 4 applicability、Clause 5 conformance、Clause 6 life-cycle data/information items、Clause 7 generic information-item types、Clause 8 lifecycle-process mapping、Clause 9 records、Clause 10 specific information-item contents 以及全部 annexes。

该结构说明研究入口，不构成条款结论。Agent 必须在 source gate 后建立完整 inventory，并允许实际条款内容修正本说明中的初始假设。

### Research questions carried by this task

- **RQ1**: 复杂系统 Verification 的规范性基础是什么？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ5**: Verification Evidence 如何通过可审查的 Assurance Argument 支持 Compliance Claim？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ7**: DBSE Verification Workflow 如何形成机器可解释、可查询和可检查的 MBSE information model？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。

### Innovation candidates under test

- **INN-T2** — typed Verification Basis -> Verification Obligation -> Strategy 的框架中间对象链。Falsification condition: 既有 standards/research 已定义等价 obligation 对象、typed basis 与生命周期关系。Non-claim: 不声称标准普遍从 requirement 直接跳到 test。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-T3** — Evidence identity、provenance、applicability、credibility 与 sufficiency 的分离模型。Falsification condition: 既有 assurance/evidence metamodel 已提供等价谓词和关系。Non-claim: 不把 Evidence 或 Claim-Argument-Evidence 概念本身主张为原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-I1** — 机器可读 verification metamodel 与非产品化研究原型。Falsification condition: 既有开源或研究平台提供等价模型和评价能力，或原型无法支持审计查询。Non-claim: 不把工程实现本身自动等同学术创新。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。

Tasks 001-021 只能返回 `SUPPORT / QUALIFY / FALSIFY / NO EVIDENCE`；Task 022 只能综合为 `SUPPORTED / QUALIFIED / FALSIFIED / OPEN`。任何任务都不能设置 `novelty established`。

### Evidence hierarchy

1. target-source normative provisions;
2. target-source informative material;
3. independently reviewed repository research on other normative sources;
4. directly checked practice-comparison sources;
5. framework hypotheses and research proposals.

低层级证据可以提出问题、比较维度或反例，但不得覆盖或替代高层级证据。Informative material 不得转成 requirement；reviewed note 不替代本任务原文研究；practice source 不生成 target-source clause record；framework hypothesis 不决定标准应当说什么。来源数量不能替代证据质量，禁止来源投票。

### Durable research interface

本任务产生的 reviewed note 是下游研究的耐久接口。执行者必须研究完整受控原文，独立评审者必须使用自己合法取得且指纹匹配的原文核验关键 locator；评审通过后，下游任务应只消费 note 中的 locator + faithful paraphrase + source class + object/relation + limitation + review disposition，而不重新进行同一标准的全文研究。研究笔记不得以“见原文”代替命题，也不取代正式标准。

### Core research principles

1. `Standard evidence -> interpretation -> framework implication -> proposal` 四层分离；
2. 先记录 source-native objects/relations/conditions，再映射 VAF；
3. 冲突、反例、ambiguity 和 `NO EVIDENCE IN THE REVIEWED SOURCE POPULATION` 必须可见；
4. standard silence 不证明 novelty，也不授权任意设计；
5. 只进行 locator-backed 的最小仓库变更；
6. V0-V12 保持 `OPEN-CANDIDATE`，不得在 source task 中冻结 schema、metamodel、state machine 或 automation interface。

### Direct practice-comparison boundary

These prompts were derived from the handbook originals, not from the pending-review handbook notes. The executing agent does not need either handbook to complete the target-standard study.


## Objective

Establish the clause-level content and relationship model for life-cycle information items, then test how far it can support the VAF conceptual information architecture without pretending that document content requirements define an executable schema.

## Required questions

- How does the standard relate process outcomes, information-item purposes and required content?
- Which distinctions among information item, record, report, plan, specification and description must be preserved?
- What mappings are supported for Verification Strategy, procedure, result, anomaly, traceability, assurance and change records?
- What remains outside the standard: identity scheme, serialization, cardinality, lifecycle state and tool automation?

## Required work and outputs

1. Verify source identity and record clause/annex inventory before extraction.
2. Produce `../standard_notes/iso_iec_ieee_15289_2019_clause_study.md` with normative/informative and modality labels.
3. Create a 15288/29148/15026-2/15289 information-item crosswalk and propose only candidate mappings to V0–V12.

## Stop conditions

Do not freeze fields, cardinalities, document names, information model, metamodel, state machine, serialization or automation interface. Until independent review is recorded, do not promote 15289-dependent conclusions, close ISO-G07C, freeze an information model, or finalize mappings in Tasks 008/012 that require reviewed 15289 evidence. This is not a global research lock: unrelated metadata verification, source acquisition, source inventory and working/candidate research may proceed under their own task gates.

## Research contribution contract

This task tests RQ1 by separating 15289 requirements from framework interpretation, RQ5 by locating the information-item boundaries of Result, Evidence Item and Argument input, and RQ7 by determining what content/document mappings do and do not imply for an executable model. It shall explicitly analyse Clause 4 applicability/work effort, Clause 5 full versus tailored conformance, Clause 6 data/record/document distinctions and information management. `Interoperability` shall be split into taxonomy/content/document mapping versus syntax, semantic exchange and tool interoperability; 15289 alone cannot close the latter.

## Candidate falsification tests

- `INN-T2`: record `FALSIFY` if 15289 already defines an equivalent typed basis-obligation-strategy intermediate object; otherwise distinguish partial support from silence.
- `INN-T3`: test whether source-native information management already separates evidence identity, provenance, applicability and credibility at equivalent scope.
- `INN-I1`: test whether the standard supplies executable identity, cardinality, state and serialization semantics; content headings alone are not support.

## Negative findings and non-answers

Record every absent schema/state/cardinality/serialization rule as `NO EVIDENCE`, not as permission to invent it or as novelty proof. A content mapping cannot establish tool interoperability, assurance sufficiency or a universal document instance.

## Generalization rights

Source-native lifecycle information concepts may be proposed for `Generic`; source-specific document views remain `Extension`; project packaging/naming remains `Practice`; executable-schema conclusions remain `No adoption` pending later evidence.

## Synthesis handoff dataset

Emit one record per used proposition with the common README data contract, plus `item_family`, `content_or_document_relation`, `interoperability_dimension`, `result_evidence_argument_boundary` and `schema_non_answer`. Task 022 consumes only independently reviewed records.

## Detailed execution specification

### Execution outcome

The agent shall leave a reviewable clause study, a reproducible evidence trail and a bounded repository delta. A narrative summary alone is not an acceptable result. The study shall determine what ISO/IEC/IEEE 15289:2019 actually requires for life-cycle information items, how those requirements depend on life-cycle processes, and where the VAF must remain framework-defined.

### Stage 0 — source and repository gate

Before interpreting any clause:

1. confirm the local file path, canonical title, edition, publication date, page count and SHA-256 against the control record;
2. inspect the title page, copyright page, table of contents, normative references, terms, all main clauses and annex classifications;
3. record any missing, unreadable or duplicated pages and stop if identity or completeness cannot be established;
4. record the starting commit/branch and current statuses of ISO-G07, ISO-G07A/B/C and LC-G04;
5. do not commit the licensed PDF or reproduce substantial source text.

If a replacement is formally published before extraction starts, stop and issue a retarget decision. If publication occurs during the study, preserve the 2019 source-native record and assess migration explicitly; do not silently mix editions.

### Stage 1 — complete clause inventory

Create an inventory covering every main clause and annex. For each entry record: locator, title, normative/informative status, subject, relevance (`primary`, `supporting`, `context`, `none`) and extraction disposition. No clause may disappear merely because it appears unrelated; excluded clauses receive a one-line rationale.

### Stage 2 — mandatory research packages

The study shall separately analyse:

1. scope, conformance, tailoring and stated relationship to ISO/IEC/IEEE 15288 and other normative references;
2. the standard's definitions of information item, information-item content and life-cycle information;
3. the rule connecting a process, its outcomes, its information items and the required content of those items;
4. generic content requirements and the specialised content groups for plans, procedures, descriptions, specifications, requests, reports and records;
5. distinctions among purpose, content, format, medium, name and physical document instance;
6. verification-, validation-, configuration-, problem-, decision-, review- and assurance-related information;
7. tailoring, aggregation, decomposition, combined documents and applicability conditions;
8. annex examples, mappings or guidance, explicitly separated from normative requirements.

### Stage 3 — clause evidence record

For every proposition used in a repository conclusion, capture:

| Field | Required content |
|---|---|
| Locator | exact clause/table/figure/annex identifier and PDF page |
| Source class | definition, normative requirement, recommendation, permission, note, example or annex guidance |
| Modality | exact `shall`/`should`/`may`/descriptive classification without long quotation |
| Source intent | faithful paraphrase of what the source controls |
| Native objects | process, outcome, information item, content element, relation, role or record |
| Conditions | applicability, tailoring, lifecycle or conformance conditions |
| Framework implication | consequence for VAF, written separately from source intent |
| Confidence | confirmed, ambiguous or review-needed |
| Destination | note/table/gap/register location receiving the conclusion |

Use the reasoning chain `Standard evidence → interpretation → framework implication → proposal`. Never merge these layers into one sentence.

### Stage 4 — required mappings

Produce at least four matrices:

1. `15288 process/outcome → 15289 information-item purpose/content`;
2. `VAF concept → candidate 15289 information-item class → locator → limitation`;
3. `29148/15026-2/15289 object or view → alignment/conflict/no-equivalence`;
4. `V0–V12 → consumed/produced/updated information → source support → framework extension`.

The VAF mapping shall explicitly cover Verification Basis, Verification Obligation, Verification Strategy, Verification Case/Procedure, Result, Evidence Item, Evidence Provenance, Anomaly, change/re-verification, Sufficiency Assessment and Closure/decision records. Absence of an explicit standard item is a finding, not permission to invent one.

### Stage 5 — repository deliverables

The agent shall:

- create `../standard_notes/iso_iec_ieee_15289_2019_clause_study.md` with metadata, method, inventory, clause findings, mappings, limitations and conclusions;
- update `../standards_map.md` only where a clause-level locator supports the cell;
- update `../normative_gap_matrix.md`, especially ISO-G07/B/C and LC-G04, without closing a gap on document-content evidence alone;
- update `../consolidation/architecture_impact_register.md` with one disposition per affected concept;

- create an independent-review record under `../reviews/` containing scope, source fingerprint, changed files, major conclusions, open issues and reviewer checklist.

Crosswalk rows involving unreviewed downstream sources are `provisional` and shall identify a downstream closure owner. Task 001 closes only its own 15289 source-native findings and reviewed VAF implications; it does not finalize Part 3, Part 4 or architecture-synthesis conclusions for sources not yet reviewed.

### Architecture decision rules

Use only `CONFIRM`, `EXTEND`, `MODIFY`, `SPLIT`, `MERGE`, `DEPRECATE`, `NO-IMPACT` or `DEFERRED`. `EXTEND`, `MODIFY`, `SPLIT`, `MERGE` and `DEPRECATE` require affected objects, compatibility risk and migration notes. Content requirements may support a conceptual item/view; they do not by themselves support field identity, universal cardinality, lifecycle state, serialization, API or database schema.

### Required conclusions

The report shall answer explicitly:

- whether ISO-G07C can advance, and exactly what remains open;
- whether the standard supports a taxonomy, a content model, an interoperability mapping, or some combination;
- which proposed VAF item names are source-native and which remain framework-defined;
- whether any current V0–V12 input/output relation is contradicted or incomplete;
- what evidence would still be required before an executable information model could be designed.

### No-overclaim rules

Do not state that ISO 15289 defines the VAF schema, mandates one document per information item, fixes filenames or storage formats, defines V0–V12, or closes evidence sufficiency. Do not convert annex examples into mandatory content. Do not infer absence of an information need from absence of a named document.

### Mandatory execution sequence and report structure

Execute in this order: snapshot repository state; pass the source gate; build and reconcile the complete clause inventory; extract evidence package by package; record contradictions/ambiguities; draft the note; build the required matrices; apply the smallest repository delta; run a whole-repository consistency sweep; prepare the independent-review packet; stop at `REVIEW PENDING`.

The research note shall contain, in order: document control and source fingerprint; scope/conformance/normative dependencies; research method and clause coverage; controlled terminology; process–outcome–information model; generic content rules; item-family findings; verification-assurance item findings; annex/guidance findings; four required crosswalks; V0–V12 assessment; gap dispositions; Architecture Impact dispositions and migrations; contradictions/uncertainties; repository changes; open questions; final conclusions; and review handoff.

The review packet shall contain the starting/head commit, source fingerprint, clause-coverage reconciliation, claims-to-locators table, changed-file list, status transitions, architecture-impact summary, known limitations, copyright check and reviewer acceptance checklist. A reviewer must be able to audit every promoted conclusion without reconstructing the agent's reasoning from chat history.

The note must define key terminology and carry enough locator-backed paraphrase and classification that a downstream task can consume reviewed conclusions without reopening the source. Independent source review still requires a legally obtained, fingerprint-matching original.

### Repository consistency checks

### Definition of done

This task is complete only when the source gate and full inventory are recorded; every material 15289 conclusion has a locator and classification; all four matrices exist with downstream-dependent rows explicitly provisional; contradictory and ambiguous evidence is visible; all affected repository files agree on source/study/review status; `git diff --check`, relative-link checks and terminology/status sweeps pass; the review packet can reproduce the conclusions without the PDF; and an independent review disposition is recorded. Until then the status remains `CLAUSE STUDY IN PROGRESS` or `REVIEW PENDING`, never `reviewed`. Completion of Task 001 does not require later sources to be researched.
