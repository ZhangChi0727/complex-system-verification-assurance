## Research orientation

执行本任务前必须先读取本节与 frontmatter dependencies，并带着明确的研究问题、候选反证路径和来源边界进入原文。任务不是一般性总结，也不是为当前框架寻找支持。

### Task purpose and research attitude

研究 system/software assurance process views、assurance claim 与 assurance information 的生命周期关系，检查 assurance maintenance、change 与 re-assurance 机制。

本任务服务于 `research_scope.md` 的三层目标：产品无关 Verification Methodology -> Model-Based Verification Architecture -> 非产品化 Verification Platform 研究原型。标准明确规定的内容形成构建约束；标准没有回答的内容形成 gap 或 innovation-space observation。`Standard wins over current framework hypothesis`；标准沉默不得由 agent 补齐，也不得作为 novelty proof。

### Source-specific research entry

受控 48 页原文只包含 Clauses 1–7、Bibliography 和 IEEE notices；不存在 Annex population。目录将 Clause 5 key concepts 与 Clause 6 system assurance process view、Clause 7 software assurance process view 分开，并把 process-view activities 映射到生命周期过程。

该结构说明研究入口，不构成条款结论。Agent 必须在 source gate 后建立完整 inventory，并允许实际条款内容修正本说明中的初始假设。

### Research questions carried by this task

- **RQ2**: 复杂系统 Verification 的完整生命周期是什么？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ4**: 如何定义 Verification Sufficiency，且为什么 Requirement Coverage 本身不足以证明充分性？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ5**: Verification Evidence 如何通过可审查的 Assurance Argument 支持 Compliance Claim？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。

### Innovation candidates under test

- **INN-T1** — Verification Sufficiency 的显式推理接口与残差处理语义。Falsification condition: 既有通用标准或文献已给出等价、可执行且跨证据类型的完整语义。Non-claim: 不宣称已研究标准未定义 sufficiency 即证明原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-T3** — Evidence identity、provenance、applicability、credibility 与 sufficiency 的分离模型。Falsification condition: 既有 assurance/evidence metamodel 已提供等价谓词和关系。Non-claim: 不把 Evidence 或 Claim-Argument-Evidence 概念本身主张为原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-M1** — 风险与影响驱动的 re-verification selection 方法。Falsification condition: 更广标准或文献已规定等价 selection 方法，或实例评价不能优于透明基线。Non-claim: 不预设标准只要求重验而不定义选择。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。

Tasks 001-021 只能返回 `SUPPORT / QUALIFY / FALSIFY / NO EVIDENCE`；Task 022 只能综合为 `SUPPORTED / QUALIFIED / FALSIFIED / OPEN`。任何任务都不能设置 `novelty established`。

### Evidence hierarchy

1. target-source normative provisions;
2. target-source informative material;
3. independently reviewed repository research on other normative sources;
4. directly checked practice-comparison sources;
5. framework hypotheses and research proposals.

低层级证据可以提出问题、比较维度或反例，但不得覆盖或替代高层级证据。Informative material 不得转成 requirement；reviewed note 不替代本任务原文研究；practice source 不生成 target-source clause record；framework hypothesis 不决定标准应当说什么。来源数量不能替代证据质量，禁止来源投票。

### Durable research interface

本任务产生的 reviewed note 是下游研究的耐久接口。执行者必须研究完整受控原文，独立评审者必须使用自己合法取得且指纹匹配的原文核验关键 locator；评审通过后，下游任务应只消费 note 中的 locator + faithful paraphrase + source class + object/relation + limitation + review disposition，而不重新进行同一标准的全文研究。研究笔记不得以“见原文”代替命题，也不取代正式标准。

### Core research principles

1. `Standard evidence -> interpretation -> framework implication -> proposal` 四层分离；
2. 先记录 source-native objects/relations/conditions，再映射 VAF；
3. 冲突、反例、ambiguity 和 `NO EVIDENCE IN THE REVIEWED SOURCE POPULATION` 必须可见；
4. standard silence 不证明 novelty，也不授权任意设计；
5. 只进行 locator-backed 的最小仓库变更；
6. V0-V12 保持 `OPEN-CANDIDATE`，不得在 source task 中冻结 schema、metamodel、state machine 或 automation interface。


## Objective

Determine how assurance activities, claims, evidence and assurance cases are planned, maintained and integrated across the life cycle, including the software-life-cycle view.

## Required questions

- Which assurance activities and information relationships are normative, and how do they relate to 15026-1 concepts?
- How are assurance planning, maintenance, change, evidence and decision interfaces represented?
- What is the relationship to 12207:2026 and the software view used by 24748-3?
- Which findings affect V0, V10, V11 or V12 without defining a new universal workflow?

## Detailed execution specification

### Execution outcome and prerequisite

The work shall produce a clause-level assurance-life-cycle study grounded in the published 2021 edition. If only a draft, DIS, preview or catalogue abstract is available, update the acquisition blocker and stop. Task 003's reviewed 2025 vocabulary findings must be used as the current terminology layer; version tension must be recorded, not silently normalized.

### Source-control gate

Verify the exact published edition and record only canonical title, edition/date, page count, language, SHA-256, completeness and legal-acquisition status; never record license identity, account, download time, watermark, internal URL or absolute user path. Inventory Clauses 1–7, the Bibliography and IEEE notices with their status. Record explicitly: `No annex population in the controlled 2021 source`. Licensed source content must not enter Git.

If a replacement is formally published before extraction starts, stop and issue an explicit retarget decision rather than silently using the DIS or mixing editions.

### Mandatory research packages

Analyse separately:

1. scope, conformance, intended users and normative dependencies;
2. assurance objectives, assurance planning and integration with the life cycle;
3. claim, argument, evidence and assurance-case creation/use/maintenance;
4. assurance activities, responsibilities, independence or assessment roles where actually stated;
5. monitoring, change, impact analysis, re-assurance and evidence maintenance;
6. uncertainty, confidence, sufficiency and decision/acceptance boundaries;
7. software-life-cycle process interfaces and the relationship to 12207;
8. information items and their relationship to 15289 and Parts 1–3;
9. back matter (Bibliography and IEEE notices) for boundary/provenance control only; `No annex population in the controlled 2021 source`.

For Clauses 6 and 7, build a complete row population for every outcome, task and guidance statement, classified as system-assurance view or software-assurance view. Each row shall distinguish `achieve claim` from `show achievement`, identify assurance-information input/output, planning/monitoring/change/re-assurance triggers and any stated decision point. Sampling is not permitted.

### Extraction and classification

For every used proposition record exact locator/PDF page, source class, modality, paraphrase, objects/relations, preconditions, lifecycle timing, framework implication, confidence and destination. Classify the implication as `DIRECT SUPPORT`, `INDIRECT SUPPORT`, `PROFILE/CONTEXT`, `FRAMEWORK INTERPRETATION`, `RESEARCH PROPOSAL` or `NO IMPACT`.

Do not treat guidance as a universal workflow, claim that an assurance case itself approves a system, equate process completion with sufficient assurance, or invent mandatory ownership/state/cardinality. Do not use a draft locator as the source for the published standard.
