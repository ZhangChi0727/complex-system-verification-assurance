## Objective

Establish the 29119-series conceptual vocabulary and boundaries needed to study test processes, documentation and techniques without equating testing with all verification.

## Required questions

- How are test, testing, test basis, test condition, test case, procedure, result, incident, coverage and completion distinguished?
- How does the standard separate dynamic testing, static testing and broader V&V concepts?
- Which terms can map to VAF objects and which remain software-testing specializations?
- What dependencies govern Parts 2, 3 and 4?

## Required work and outputs

Reconfirm the controlled source fingerprint at task start; produce `../standard_notes/iso_iec_ieee_29119_1_2022_clause_study.md`; build a terminology crosswalk to ISO 15288 and current VAF terms; record candidate gap and architecture impacts; obtain independent review before using Part 1 vocabulary as established basis.

## Stop conditions

Do not redefine Verification as Testing, claim a complete coverage model or promote source status before identity review.

## Detailed execution specification

### Execution outcome

Produce the controlled vocabulary and conceptual boundary required for Tasks 007–009. The report must make software testing usable as a VAF specialization without collapsing all verification into dynamic testing.

### Source gate and inventory

Recompute and confirm the controlled fingerprint, inspect title/copyright/contents, and inventory every clause, figure, table and annex. Record normative versus informative status and relevance. Resolve any edition labels or amendment/corrigendum ambiguity before extraction.

### Mandatory research packages

1. scope of the 29119 series, conformance and relation among Parts 1–4;
2. test/testing, test object/item, test basis, test condition, test case, test procedure/script, test data and test environment;
3. expected result, actual result, test result, verdict, incident/anomaly and completion;
4. static testing, dynamic testing and their relationship to verification/validation;
5. test level/type, technique, coverage item/measure and completion criteria;
6. test process, activity, task, role and information-item relations;
7. risk-based testing, selection/prioritization and contextual tailoring where present;
8. boundaries with ISO 15288 methods and VAF framework-defined concepts.

### Terminology evidence record

Every adopted or rejected term must have exact locator/PDF page, source class, definition or faithful paraphrase, synonyms/related terms, broader/narrower relation, context, proposed VAF mapping, collision risk and disposition. Definitions from normative references must be traced to their actual source when material.

### Required mapping products

- 29119 term → ISO 15288 term → VAF term → relation/limitation;
- Verification Method → testing profile → Technique → Condition → Case → Procedure → Result;
- test basis/condition/coverage item → Verification Basis/Obligation/Coverage model;
- incident/result/verdict → Anomaly/Evidence/Assessment boundary;
- Part 1 concept → required dependency for Parts 2, 3 and 4.

The report must explicitly classify each concept as `GENERIC CANDIDATE`, `SOFTWARE-TESTING PROFILE`, `FRAMEWORK-DEFINED`, `CONFLICT`, or `NO IMPACT`.

### Repository deliverables

Create `../standard_notes/iso_iec_ieee_29119_1_2022_clause_study.md`; update terminology and standards map with locators; update ISO-G02B/ISO-G04/ISO-G07 only where concept evidence exists; record Architecture Impact dispositions; update baseline/HANDOFF/CHANGELOG; and create an independent-review packet containing the complete term crosswalk and downstream constraints for Tasks 007–009.

### Required final answers

State which testing concepts can be reused generically, which require a software-testing profile, whether the source supports any part of the Oracle proposal, and what it does not establish about verification sufficiency, certification or universal coverage.

### No-overclaim rules

Do not say testing equals verification, a verdict equals evidence sufficiency, coverage percentage equals assurance, or software technique taxonomy is universal. Do not silently replace established VAF terms when the relation is only approximate.

### Mandatory execution sequence and report structure

Execute in this order: verify source; inventory clauses; extract the complete controlled vocabulary; construct concept relations; compare ISO 15288/VAF terms; classify generic versus profile concepts; establish Parts 2–4 dependency constraints; update repository; run term/link checks; prepare review; stop.

The note shall contain: source/conformance; series architecture; clause inventory; controlled glossary; test object/basis/condition/case/procedure/result model; static/dynamic/V&V boundary; coverage/completion concepts; process/information concepts; ISO/VAF crosswalk; generic/profile decisions; gap/architecture effects; limitations; repository delta; conclusions and handoff.

The review packet shall reconcile every adopted/rejected term and all primary clauses, list collisions and changed files/statuses, and verify that downstream tasks cannot misread profile terminology as Generic Core semantics.

### Definition of done

Done requires complete inventory; locator-backed controlled glossary; all five mappings; explicit generic/profile decisions; downstream Part 2–4 dependency notes; synchronized repository statuses; clean link/diff/term scans; and independent review approval.
