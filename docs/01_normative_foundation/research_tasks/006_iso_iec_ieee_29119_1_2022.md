## Research orientation

执行本任务前必须先读取本节与 frontmatter dependencies，并带着明确的研究问题、候选反证路径和来源边界进入原文。任务不是一般性总结，也不是为当前框架寻找支持。

### Task purpose and research attitude

建立 ISO/IEC/IEEE 29119 family 的 testing concepts、test model、process/document/technique 关系和术语边界，为 Parts 2-4 的后续映射提供受控基础。

本任务服务于 `research_scope.md` 的三层目标：产品无关 Verification Methodology -> Model-Based Verification Architecture -> 非产品化 Verification Platform 研究原型。标准明确规定的内容形成构建约束；标准没有回答的内容形成 gap 或 innovation-space observation。`Standard wins over current framework hypothesis`；标准沉默不得由 agent 补齐，也不得作为 novelty proof。

### Source-specific research entry

原文作为 Part 1 concepts and definitions 基础，研究需覆盖 testing context、test process/model、test basis/item/condition/case/procedure、result/verdict、coverage、risk-based testing 及与其他 parts 的关系。

该结构说明研究入口，不构成条款结论。Agent 必须在 source gate 后建立完整 inventory，并允许实际条款内容修正本说明中的初始假设。

### Research questions carried by this task

- **RQ3**: 如何系统确定 Level + Method + Technique + Environment + Oracle + Coverage + Evidence？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ5**: Verification Evidence 如何通过可审查的 Assurance Argument 支持 Compliance Claim？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ7**: DBSE Verification Workflow 如何形成机器可解释、可查询和可检查的 MBSE information model？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。

### Innovation candidates under test

- **INN-T2** — typed Verification Basis -> Verification Obligation -> Strategy 的框架中间对象链。Falsification condition: 既有 standards/research 已定义等价 obligation 对象、typed basis 与生命周期关系。Non-claim: 不声称标准普遍从 requirement 直接跳到 test。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-M3** — population + criterion + evidence + disposition 的可计算 coverage 模型。Falsification condition: 既有 coverage metamodel 等价，或跨实例无法保持可比且可扩展。Non-claim: 不主张任何 universal percentage 或 completion rule。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-M4** — 将 expected-result 正确性依据建模为受控 Oracle 候选对象。Falsification condition: ISO/IEC 9646、testing literature 或其他来源已有等价对象与控制语义，或实例不需要独立对象。Non-claim: 不把 expected result 自动重标为 Oracle。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-I2** — conformance-testing 与 lifecycle-assurance 传统之间的受控映射模型。Falsification condition: ISO/IEC 9646、29119、15026 或既有研究已经给出等价统一模型。Non-claim: 不预设 PICS、test purpose 或 verdict 映射为原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。

Tasks 001-021 只能返回 `SUPPORT / QUALIFY / FALSIFY / NO EVIDENCE`；Task 022 只能综合为 `SUPPORTED / QUALIFIED / FALSIFIED / OPEN`。任何任务都不能设置 `novelty established`。

### Evidence hierarchy

1. target-source normative provisions;
2. target-source informative material;
3. independently reviewed repository research on other normative sources;
4. directly checked practice-comparison sources;
5. framework hypotheses and research proposals.

低层级证据可以提出问题、比较维度或反例，但不得覆盖或替代高层级证据。Informative material 不得转成 requirement；reviewed note 不替代本任务原文研究；practice source 不生成 target-source clause record；framework hypothesis 不决定标准应当说什么。来源数量不能替代证据质量，禁止来源投票。

### Durable research interface

本任务产生的 reviewed note 是下游研究的耐久接口。执行者必须研究完整受控原文，独立评审者必须使用自己合法取得且指纹匹配的原文核验关键 locator；评审通过后，下游任务应只消费 note 中的 locator + faithful paraphrase + source class + object/relation + limitation + review disposition，而不重新进行同一标准的全文研究。研究笔记不得以“见原文”代替命题，也不取代正式标准。

### Core research principles

1. `Standard evidence -> interpretation -> framework implication -> proposal` 四层分离；
2. 先记录 source-native objects/relations/conditions，再映射 VAF；
3. 冲突、反例、ambiguity 和 `NO EVIDENCE IN THE REVIEWED SOURCE POPULATION` 必须可见；
4. standard silence 不证明 novelty，也不授权任意设计；
5. 只进行 locator-backed 的最小仓库变更；
6. V0-V12 保持 `OPEN-CANDIDATE`，不得在 source task 中冻结 schema、metamodel、state machine 或 automation interface。


## Objective

Establish the 29119-series conceptual vocabulary and boundaries needed to study test processes, documentation and techniques without equating testing with all verification.

## Required questions

- How are test, testing, test basis, test model, test design technique, coverage item, test case, procedure, result, incident and completion distinguished in the current edition?
- How does the standard separate dynamic testing, static testing and broader V&V concepts?
- Which terms can map to VAF objects and which remain software-testing specializations?
- What dependencies govern Parts 2, 3 and 4?

## Stop conditions

Do not redefine Verification as Testing, claim a complete coverage model or promote source status before identity review.

## Research contribution contract

This task answers RQ3/RQ5/RQ7 by establishing the second-edition `test model` centred vocabulary and the conditions under which testing is a specialization of Verification. It shall distinguish static/dynamic testing, coverage, completion and evidence/claim boundaries, and build an edition-transition collision register for historical `test condition` usage.

## Candidate falsification tests

Test `INN-T2/M3/M4/I2` against the current chain `test basis → test model → test design technique → test coverage items → test cases → test procedures → actual/test result → verdict/incident/report`. Record equivalence only when relation, scope and lifecycle role match.

## Negative findings and non-answers

`Test condition` is historical/collision terminology, not a fixed current intermediate entity. Testing does not equal all Verification; completion criteria do not establish assurance sufficiency; the series does not by itself provide a universal schema or Oracle.

## Generalization rights

Current terminology initially enters `Profile`; only independently cross-standard-supported relations may become `Generic`; project test naming remains `Practice`.

## Synthesis handoff dataset

Emit the common record plus `edition_term`, `current_term`, `collision_status`, `test_model_relation`, `testing_subset_condition`, `coverage_completion_limit` and `profile_promotion_evidence`.

## Detailed execution specification

### Execution outcome

Produce the controlled vocabulary and conceptual boundary required for Tasks 007–009. The report must make software testing usable as a VAF specialization without collapsing all verification into dynamic testing.

### Source gate and inventory

Recompute and confirm the controlled fingerprint, inspect title/copyright/contents, and inventory every clause, figure, table and annex. Record normative versus informative status and relevance. Resolve any edition labels or amendment/corrigendum ambiguity before extraction.

### Mandatory research packages

1. scope of the 29119 series, conformance and relation among Parts 1–4;
2. test/testing, test object/item, test basis, test model, test design technique, test coverage item, test case, test procedure/script, test data and test environment; record `test condition` only in the edition-transition/collision register;
3. expected result, actual result, test result, verdict, incident/anomaly and completion;
4. static testing, dynamic testing and their relationship to verification/validation;
5. test level/type, technique, coverage item/measure and completion criteria;
6. test process, activity, task, role and information-item relations;
7. risk-based testing, selection/prioritization and contextual tailoring where present;
8. boundaries with ISO 15288 methods and VAF framework-defined concepts.

### Terminology evidence record

Every adopted or rejected term must have exact locator/PDF page, source class, definition or faithful paraphrase, synonyms/related terms, broader/narrower relation, context, proposed VAF mapping, collision risk and disposition. Definitions from normative references must be traced to their actual source when material.

### Required mapping products

- 29119 term → ISO 15288 term → VAF term → relation/limitation;
- `test basis → test model → test design technique → test coverage item → test case → test procedure → actual/test result → verdict/incident/report`;
- test basis/model/coverage item → Verification Basis/Obligation/Coverage model, distinguishing direct source relations from framework synthesis;
- incident/result/verdict → Anomaly/Evidence/Assessment boundary;
- Part 1 concept → required dependency for Parts 2, 3 and 4.

The report must explicitly classify each concept as `GENERIC CANDIDATE`, `SOFTWARE-TESTING PROFILE`, `FRAMEWORK-DEFINED`, `CONFLICT`, or `NO IMPACT`.

### Repository deliverables

Create `../standard_notes/iso_iec_ieee_29119_1_2022_clause_study.md`; update terminology and standards map with locators; update ISO-G02B/ISO-G04/ISO-G07 only where concept evidence exists; record Architecture Impact dispositions; update baseline/HANDOFF/CHANGELOG; and create an independent-review packet containing the complete term crosswalk and downstream constraints for Tasks 007–009.

### Required final answers

State which testing concepts can be reused generically, which require a software-testing profile, whether the source supports any part of the Oracle proposal, and what it does not establish about verification sufficiency, certification or universal coverage.

### No-overclaim rules

Do not say testing equals verification, a verdict equals evidence sufficiency, coverage percentage equals assurance, or software technique taxonomy is universal. Do not silently replace established VAF terms when the relation is only approximate.

### Mandatory execution sequence and report structure

Execute in this order: verify source; inventory clauses; extract the complete controlled vocabulary; construct concept relations; compare ISO 15288/VAF terms; classify generic versus profile concepts; establish Parts 2–4 dependency constraints; update repository; run term/link checks; prepare review; stop.

The note shall contain: source/conformance; series architecture; clause inventory; controlled glossary; edition-transition/collision register; current test-basis/model/technique/coverage/case/procedure/result chain; static/dynamic/V&V boundary; coverage/completion concepts; process/information concepts; ISO/VAF crosswalk; generic/profile decisions; gap/architecture effects; limitations; repository delta; conclusions and handoff.

The review packet shall reconcile every adopted/rejected term and all primary clauses, list collisions and changed files/statuses, and verify that downstream tasks cannot misread profile terminology as Generic Core semantics.
