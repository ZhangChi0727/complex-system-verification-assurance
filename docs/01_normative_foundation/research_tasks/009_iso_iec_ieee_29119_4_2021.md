## Research orientation

执行本任务前必须先读取本节与 frontmatter dependencies，并带着明确的研究问题、候选反证路径和来源边界进入原文。任务不是一般性总结，也不是为当前框架寻找支持。

### Task purpose and research attitude

研究 specification-based、structure-based、experience-based test design techniques 及其 coverage measures，检验可复用 Verification Pattern 与可计算 coverage 的边界。

本任务服务于 `research_scope.md` 的三层目标：产品无关 Verification Methodology -> Model-Based Verification Architecture -> 非产品化 Verification Platform 研究原型。标准明确规定的内容形成构建约束；标准没有回答的内容形成 gap 或 innovation-space observation。`Standard wins over current framework hypothesis`；标准沉默不得由 agent 补齐，也不得作为 novelty proof。

### Source-specific research entry

原文 Clause 5 枚举并规范 test design techniques，Clause 6 定义相应 coverage measurement；annexes 提供技术应用示例，必须与 normative requirements 分离。

该结构说明研究入口，不构成条款结论。Agent 必须在 source gate 后建立完整 inventory，并允许实际条款内容修正本说明中的初始假设。

### Research questions carried by this task

- **RQ3**: 如何系统确定 Level + Method + Technique + Environment + Oracle + Coverage + Evidence？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ4**: 如何定义 Verification Sufficiency，且为什么 Requirement Coverage 本身不足以证明充分性？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ6**: 哪些 Verification Techniques 可以抽象为产品无关的 Verification Patterns？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。

### Innovation candidates under test

- **INN-M3** — population + criterion + evidence + disposition 的可计算 coverage 模型。Falsification condition: 既有 coverage metamodel 等价，或跨实例无法保持可比且可扩展。Non-claim: 不主张任何 universal percentage 或 completion rule。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-M4** — 将 expected-result 正确性依据建模为受控 Oracle 候选对象。Falsification condition: ISO/IEC 9646、testing literature 或其他来源已有等价对象与控制语义，或实例不需要独立对象。Non-claim: 不把 expected result 自动重标为 Oracle。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-A3** — profile pattern 经受控抽象阶梯进入 generic candidate 的机制。Falsification condition: 已有 profile-extension governance 提供等价 provenance、promotion gate 和跨域验证规则。Non-claim: 不把 criticality 或 model evidence 概念据为原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。

Tasks 001-021 只能返回 `SUPPORT / QUALIFY / FALSIFY / NO EVIDENCE`；Task 022 只能综合为 `SUPPORTED / QUALIFIED / FALSIFIED / OPEN`。任何任务都不能设置 `novelty established`。

### Evidence hierarchy

1. target-source normative provisions;
2. target-source informative material;
3. independently reviewed repository research on other normative sources;
4. directly checked practice-comparison sources;
5. framework hypotheses and research proposals.

低层级证据可以提出问题、比较维度或反例，但不得覆盖或替代高层级证据。Informative material 不得转成 requirement；reviewed note 不替代本任务原文研究；practice source 不生成 target-source clause record；framework hypothesis 不决定标准应当说什么。来源数量不能替代证据质量，禁止来源投票。

### Durable research interface

本任务产生的 reviewed note 是下游研究的耐久接口。执行者必须研究完整受控原文，独立评审者必须使用自己合法取得且指纹匹配的原文核验关键 locator；评审通过后，下游任务应只消费 note 中的 locator + faithful paraphrase + source class + object/relation + limitation + review disposition，而不重新进行同一标准的全文研究。研究笔记不得以“见原文”代替命题，也不取代正式标准。

### Core research principles

1. `Standard evidence -> interpretation -> framework implication -> proposal` 四层分离；
2. 先记录 source-native objects/relations/conditions，再映射 VAF；
3. 冲突、反例、ambiguity 和 `NO EVIDENCE IN THE REVIEWED SOURCE POPULATION` 必须可见；
4. standard silence 不证明 novelty，也不授权任意设计；
5. 只进行 locator-backed 的最小仓库变更；
6. V0-V12 保持 `OPEN-CANDIDATE`，不得在 source task 中冻结 schema、metamodel、state machine 或 automation interface。


## Objective

Extract a controlled software test-technique taxonomy and distinguish technique selection, coverage items, test design and completion from ISO 15288 verification methods.

## Required questions

- Which specification-based, structure-based and experience-based techniques are defined, and with what inputs/outputs?
- How are coverage items/measures and stopping rules expressed?
- How should `Test Basis → Test Model → Technique → Coverage Item → Test Case/Data/Procedure` relations be represented?
- Which techniques are software-specific and which are plausible generic candidates?

## Required work and outputs

Verify source identity; produce `../standard_notes/iso_iec_ieee_29119_4_2021_clause_study.md`; create method-versus-technique and coverage crosswalks; update ISO-G02/ISO-G04 candidate interpretation only; record architecture impact and independent review.

## Stop conditions

Do not treat technique coverage as universal verification sufficiency, or promote an Oracle entity without reviewed support.

## Research contribution contract

This task answers RQ3/RQ4/RQ6 by exhaustively studying every Clause 5 technique and Clause 6 coverage measure, with Annexes A–H classified informative. Outputs shall use `test model / coverage item / test case / test data`, never a fixed current `test condition` layer.

## Candidate falsification tests

Test `INN-M3/M4/A3` against source-native coverage populations/criteria, expected-result construction and technique reuse. Each pattern candidate requires prerequisites, variation points, prohibited generalization, counterexample, composability and profile-to-generic promotion evidence.

## Negative findings and non-answers

Annex F effectiveness is technique-selection evidence, not sufficiency proof; Annex H provides test-model context. Coverage achievement, expected output or technique classification does not establish universal sufficiency or an Oracle object.

## Generalization rights

Techniques begin in the software-testing `Profile`; only cross-domain validated patterns may move to `Extension` or `Generic`; tool procedures remain `Practice`.

## Synthesis handoff dataset

Emit the common record plus `technique_family`, `test_model_input`, `coverage_population_measure`, `output_case_data`, `pattern_eligibility`, `counterexample`, `composability` and `sufficiency_limit`.

## Detailed execution specification

### Execution outcome and dependency gate

Produce a controlled software test-design technique taxonomy, selection model and coverage interpretation grounded in Part 1 terminology. Task 006 must be reviewed before term promotion; ambiguous cross-edition terminology stays explicit.

### Source gate and inventory

Confirm path, canonical edition/date, 148-page extent, SHA-256 and completeness. Inventory every technique clause, table, figure and annex; record whether it is normative, recommended or illustrative and whether it defines procedure, input, coverage item, measure, output, applicability or limitation.

### Mandatory technique packages

Analyse all source-defined technique families rather than sampling. Group them only after source-native classification is recorded. For each technique capture purpose, test basis, model/representation, coverage items, construction rules, expected outputs, stopping/completion rule if any, assumptions, strengths, limitations and combinations. Separately analyse selection criteria and any experience-based, specification-based, structure-based or other source-native families.

### Repository deliverables

### No-overclaim rules

Do not call every technique a verification method, generalize software structural coverage to all verification objects, infer sufficiency from achieved coverage, invent mandatory selection algorithms, or claim an expected result generator is a validated Oracle.

### Mandatory execution sequence and report structure

Execute in this order: verify dependency/source; inventory all technique clauses; extract every technique using the fixed record; reconcile the register with contents/annexes; build method/technique/coverage mappings; assess selection and Oracle implications; update repository; prepare review; stop.

The note shall contain: source control; taxonomy method; complete technique register; family-by-family findings; inputs/outputs/construction rules; coverage items/measures; selection/applicability; method-versus-technique map; coverage model; Oracle analysis; generic/profile decisions; gaps/architecture; limitations; repository delta; conclusions and handoff.

The review packet shall prove 100% technique coverage, sample construction/coverage paraphrases against locators, list changed files/statuses and check all sufficiency and generalization prohibitions.
