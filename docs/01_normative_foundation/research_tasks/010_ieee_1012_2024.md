## Research orientation

执行本任务前必须先读取本节与 frontmatter dependencies，并带着明确的研究问题、候选反证路径和来源边界进入原文。任务不是一般性总结，也不是为当前框架寻找支持。

### Task purpose and research attitude

研究基于 integrity 的 V&V rigor、independence、lifecycle V&V tasks、management/reporting/documentation 和 sufficient-evidence 机制，并检验其 Generic/Profile 推广边界。

本任务服务于 `research_scope.md` 的三层目标：产品无关 Verification Methodology -> Model-Based Verification Architecture -> 非产品化 Verification Platform 研究原型。标准明确规定的内容形成构建约束；标准没有回答的内容形成 gap 或 innovation-space observation。`Standard wins over current framework hypothesis`；标准沉默不得由 agent 补齐，也不得作为 novelty proof。

### Source-specific research entry

原文跨越 scope/conformance、V&V objectives/team/testing、management processes、system/software/hardware lifecycle V&V process tables、reporting/documentation 与 V&V Plan content；不同对象域和 integrity level 的表格必须分别研究。

该结构说明研究入口，不构成条款结论。Agent 必须在 source gate 后建立完整 inventory，并允许实际条款内容修正本说明中的初始假设。

### Research questions carried by this task

- **RQ2**: 复杂系统 Verification 的完整生命周期是什么？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ3**: 如何系统确定 Level + Method + Technique + Environment + Oracle + Coverage + Evidence？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ4**: 如何定义 Verification Sufficiency，且为什么 Requirement Coverage 本身不足以证明充分性？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ5**: Verification Evidence 如何通过可审查的 Assurance Argument 支持 Compliance Claim？ 本任务只回答与本来源及其受控 scope 直接相关的子问题；完整答案由 Task 022 综合。
- **RQ8**: 如何通过多领域实例（ARINC 615A 协议符合性验证为 first instance，无人机飞管系统验证与 LLM 服务可靠性与性能验证为后续实例）验证 framework 的 completeness、traceability、repeatability、scalability 与 reusability？ 本任务不回答或关闭 RQ8；它从 integrity、adaptive 与 AI/ML material 提取 evaluation criteria、stressor/counterexample、可观测项和失败条件，供三个实例的受控评价使用。

### Innovation candidates under test

- **INN-T1** — Verification Sufficiency 的显式推理接口与残差处理语义。Falsification condition: 既有通用标准或文献已给出等价、可执行且跨证据类型的完整语义。Non-claim: 不宣称已研究标准未定义 sufficiency 即证明原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-A1** — V0-V12 mixed-ontology 编排与可分解 Composite Gate。Falsification condition: 既有 lifecycle architecture 已提供等价编排和相同可分解 gate contract。Non-claim: 不主张 gate、review 或 decision 概念本身原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-M1** — 风险与影响驱动的 re-verification selection 方法。Falsification condition: 更广标准或文献已规定等价 selection 方法，或实例评价不能优于透明基线。Non-claim: 不预设标准只要求重验而不定义选择。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。
- **INN-A3** — profile pattern 经受控抽象阶梯进入 generic candidate 的机制。Falsification condition: 已有 profile-extension governance 提供等价 provenance、promotion gate 和跨域验证规则。Non-claim: 不把 criticality 或 model evidence 概念据为原创。执行时必须比较 purpose、objects、relations、lifecycle、authority 和 applicability，而不是只比较标签。

Tasks 001-021 只能返回 `SUPPORT / QUALIFY / FALSIFY / NO EVIDENCE`；Task 022 只能综合为 `SUPPORTED / QUALIFIED / FALSIFIED / OPEN`。任何任务都不能设置 `novelty established`。

### Evidence hierarchy

1. target-source normative provisions;
2. target-source informative material;
3. independently reviewed repository research on other normative sources;
4. directly checked practice-comparison sources;
5. framework hypotheses and research proposals.

低层级证据可以提出问题、比较维度或反例，但不得覆盖或替代高层级证据。Informative material 不得转成 requirement；reviewed note 不替代本任务原文研究；practice source 不生成 target-source clause record；framework hypothesis 不决定标准应当说什么。来源数量不能替代证据质量，禁止来源投票。

### Durable research interface

本任务产生的 reviewed note 是下游研究的耐久接口。执行者必须研究完整受控原文，独立评审者必须使用自己合法取得且指纹匹配的原文核验关键 locator；评审通过后，下游任务应只消费 note 中的 locator + faithful paraphrase + source class + object/relation + limitation + review disposition，而不重新进行同一标准的全文研究。研究笔记不得以“见原文”代替命题，也不取代正式标准。

### Core research principles

1. `Standard evidence -> interpretation -> framework implication -> proposal` 四层分离；
2. 先记录 source-native objects/relations/conditions，再映射 VAF；
3. 冲突、反例、ambiguity 和 `NO EVIDENCE IN THE REVIEWED SOURCE POPULATION` 必须可见；
4. standard silence 不证明 novelty，也不授权任意设计；
5. 只进行 locator-backed 的最小仓库变更；
6. V0-V12 保持 `OPEN-CANDIDATE`，不得在 source task 中冻结 schema、metamodel、state machine 或 automation interface。


## Objective

Determine how IEEE 1012 structures V&V processes, integrity-dependent rigor, independence, task applicability and evidence across system, software and hardware life cycles.

## Required questions

- How are V&V integrity levels established and connected to task rigor?
- When and how is independence required, and what dimensions of independence are distinguished?
- Which tasks support coverage, anomaly handling, change/reuse and completion evidence?
- How does this rigor model compare with 15026-3 and aviation assurance levels without claiming equivalence?

## Detailed execution specification

### Execution outcome

Produce a clause- and table-level model of IEEE 1012 V&V applicability, integrity-dependent rigor and independence across system, software and hardware contexts. The report must make task applicability traceable rather than merely summarize the 309-page standard.

### Source gate and coverage control

Confirm path, canonical edition/date, 309-page extent, SHA-256, completeness and amendment status. Treat Clauses 2–12 and Tables 1a–d/2a–d as the normative study population; record Tables 3, figures and Annexes A–P as informative unless an exact source marker requires a narrower classification. Because applicability may be encoded in tables, create a table inventory and verify every extracted row/footnote; do not rely only on prose or search hits. Register the apparent 12207:2008/2017 citation inconsistency in a source-errata table rather than silently correcting it.

### Mandatory research packages

1. scope, conformance, tailoring and relationship to life-cycle standards;
2. V&V concepts, processes, organization and plan;
3. integrity-level establishment, consequence/risk basis and level maintenance;
4. task applicability and rigor by integrity level, including table qualifiers and exceptions;
5. independence definitions, dimensions, required applicability and organizational/technical/managerial evidence;
6. system, software and hardware V&V task families across acquisition, development, operation, maintenance and retirement;
7. anomaly/problem reporting, corrective action, change impact, regression/re-verification and reuse;
8. V&V reporting, traceability, configuration, metrics, completion and approval boundaries;
9. tools/models and evidence credibility where explicitly addressed.

### Task/table extraction record

For each relevant task or table row record locator/PDF page, lifecycle context, integrity level(s), mandatory/conditional/recommended status, inputs, activity, outputs/evidence, responsible/independent role, completion criterion, tailoring rule, VAF mapping and limitation. Preserve footnotes and applicability conditions in paraphrase.
