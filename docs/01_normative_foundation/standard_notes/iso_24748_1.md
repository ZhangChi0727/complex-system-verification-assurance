# ISO/IEC/IEEE 24748-1:2024 Research Note

## 1. 研究边界

本笔记研究 ISO/IEC/IEEE 24748-1:2024 *Systems and software engineering — Life cycle management — Part 1: Guidelines for life cycle management*，依据 2024-03 发布的 second edition clean official edition。标准原文件仅在本地研究环境使用，不纳入版本库。

该文件的定位是生命周期管理 **guidance**：它补充 ISO/IEC/IEEE 15288 和 ISO/IEC/IEEE 12207，说明生命周期模型、阶段、过程应用、适应和管理实践。它不是新的系统生命周期过程 conformance 基准，也不把资料性附录中的示例变成强制要求。

本笔记使用以下分类：

- `GUIDANCE`：标准正文给出的指导；
- `INFORMATIVE ANNEX`：资料性附录中的说明或示例；
- `INTERPRETATION`：研究团队依据多个定位形成的受限解释；
- `FRAMEWORK IMPLICATION`：对 Verification Assurance Framework 架构的影响；
- `RESEARCH PROPOSAL`：标准没有规定、但拟在框架中研究的对象或规则。

条款编号只用于合法定位；本文全部为自行撰写的总结，不复制受版权保护的标准正文。

## 2. 总体结论

1. 生命周期模型不是过程模型，阶段也不是过程。阶段提供基于系统描述或实现状态的管理分段；过程可在任意适用阶段被选择、重复、并发或递归应用。
2. 阶段进入/退出条件、评审和 decision gate 是相关但不同的概念。条件是否满足提供决策输入；评审是一种评价机制；gate 是授权、继续、保持、重启或终止等管理决策。
3. `V0–V12` 不能作为 ISO 24748-1 的生命周期阶段，也不能因编号而被解释为标准规定的顺序。它们更适合被建模为跨过程的 Verification Assurance Process View，其中部分节点是活动，部分是组合 gate/decision。
4. Annex D 为 Verification Assurance Process View 提供了明确的指导基础：process view 可组织多个源过程的活动和任务，但不能创造并冒充源标准过程的活动或任务。
5. Annex F 的 `Verification reviews` 是候选 joint stakeholder review 类型，不是标准强制的 `Verification Readiness Review (VRR)`。生命周期/技术/管理评审也不能与 Verification Method 中的 inspection/peer review 混为一谈。
6. Annex G 支持统一 problem reporting 的价值及 category/priority 思路，但不规定通用状态机、关闭机制或框架中的 `PR` 对象。
7. Clause 6 对适应、过程—阶段映射及理由记录提供指导，因此值得新增 Lifecycle/Process Tailoring and Instantiation Record；其字段仍是框架提案。
8. ISO/IEC/IEEE 24748-2:2024 曾被列为高优先级下一步，因为 24748-1 明确将 ISO 15288 的系统工程应用指导指向该部分；该 targeted review 已于 2026-08-16 完成，结论见独立 supporting-source note。

其中 `Composite Gate` 是 Framework 为区分 assessment、review、authorization decision 和 baseline/state event 而采用的候选抽象，不是 ISO/IEC/IEEE 24748-1 的原生术语。

## 3. 范围、术语与概念边界

### 3.1 Clause 1 — Scope

**GUIDANCE — Clause 1**

- 提供生命周期管理指导，并与 ISO/IEC/IEEE 15288、ISO/IEC/IEEE 12207 配套使用；
- 提供生命周期与阶段的共同框架；
- 说明如何在生命周期中应用和适应过程；
- Clause 2 没有 normative references。

本文件作为 lifecycle-management guidance 的角色及其与 ISO/IEC/IEEE 15288、ISO/IEC/IEEE 12207 的关系，应依据标准 title、Introduction 和 Clause 1 Scope 综合判断；不能仅从 Clause 2 推导其 conformance 定位，也不应将它视为替代 ISO 15288 的 system-life-cycle process conformance baseline。

### 3.2 Clause 3 — Selected terms

| Concept | Locator | Research summary | Boundary |
|---|---|---|---|
| Life cycle | 3.24 | 从构想到退役的演化 | 生命周期本身不因标准示例而天然分成固定阶段 |
| Life cycle model | 3.25 | 由生命周期相关过程和活动构成的框架，可组织为阶段，并提供共同理解和沟通参照 | 不等于 process model |
| Stage | 3.48 | 与系统描述或实现状态有关的一段生命周期期间，通常对应重大进展或里程碑 | 不等于 process；阶段可以重叠 |
| Problem | 3.29 | 需要调查和纠正行动的困难或非期望情况 | 不能自动等同于项目自定义的 PR、anomaly 或 incident |
| Requirement | 3.39 | 表达或转化 need，并包含相关 constraints 和 conditions 的陈述 | 与 ISO 15288:2023 的术语边界一致 |

`Process view` 不是 Clause 3 的独立术语；其结构和约束来自 Annex D，必须按资料性指导处理。

## 4. Clause 4 — 生命周期概念

### 4.1 生命周期模型、阶段与决策

**GUIDANCE — 4.3.1–4.3.2**

- 生命周期模型用与决策相关的概念分段组织生命周期。
- 阶段转换通常对应 decision point，并由阶段进入/完成条件辅助判断。
- 条件通常以已完成任务、过程 outcome 或开始后续工作所需的 readiness 表达。
- 生命周期模型具有阶段，不代表脱离模型的系统生命周期天然具有这些阶段。
- 同一系统可同时处在多个阶段；阶段可以重叠、并行、非顺序或重复。
- 阶段可因条件满足或外部事件开始/结束。
- gate 决策可包括开始后续阶段、继续、重启另一阶段、保持或终止。
- decision gate 可以与 milestone 或 review 结合，可位于阶段中或阶段边界。

**INTERPRETATION**

Figure 8 表明，条件满足、评审发生和 gate decision 不是同一事件：进入/退出条件可能在决策前、同时或之后满足，外部事件也可能驱动决策。框架不得用单一 `review_complete=true` 替代 readiness assessment 与授权决策。

### 4.2 Enabling systems 与 SoS

**GUIDANCE — 4.3.3**

- enabling system 有自己的生命周期，并应与被支持系统的生命周期关联、同步；
- enabling system 可以采用不同生命周期模型；
- system-of-systems 的组成系统可能处于不同阶段并采用不同模型。

**FRAMEWORK IMPLICATION**

Verification Environment、工具链和测试设施不能仅作为静态属性；它们可能是需单独规划、验证、配置和同步的 enabling systems。

## 5. Clause 5 — 阶段中的过程应用

**GUIDANCE — Clause 5**

- 阶段是应用过程的框架；过程不等于阶段。
- 过程可在生命周期任意适用点调用，标准不规定统一的过程顺序或时点。
- 过程可以并发、迭代、递归，并受时间和项目语境影响。
- 概念、开发、生产、利用、支持、退役是示例性阶段集，不是强制的单一路径。
- 常见阶段 outcome 包括：计划及退出条件、风险与缓解、technical debt 评价、enabling systems 可用、退出条件达成、继续授权，以及信息项的生成或更新。
- 开发阶段可形成 verification/validation 结果与 assurance evidence，为决策提供支撑。

**INTERPRETATION**

阶段 outcome 和退出条件可以约束 Verification Assurance，但并不定义通用的 Verification Closure。框架需要把“证据已准备”“条件已满足”“评审已完成”“授权已作出”和“配置已基线化”建模为可区分的状态或事件。

## 6. Clause 6 — 生命周期与过程适应

### 6.1 适应输入

**GUIDANCE — 6.2.2–6.2.5**

- 识别项目和组织语境、政策、法规、伦理、安全、网络安全、隐私、风险与 IV&V 等约束；
- 让受影响方参与，并考虑 business/mission/contract needs、反馈和经验；
- 根据 system、software 或 SoS 的性质选择适用标准；
- 选择可串行、重复、组合或并行的开发方式；
- 把生命周期过程映射到所选 development approach 和 lifecycle model，并分别考虑系统、系统元素及 enabling systems。

这里提及 IV&V 只说明适应时应考虑相关政策或语境，不构成通用 Verification independence 等级要求。

### 6.2 阶段与过程映射

**GUIDANCE — 6.2.6–6.2.8**

- 确定阶段、进入/退出条件、串行/并行/组合关系、outcomes、milestones 和 gates；
- 选择并确定实现阶段 outcome 所需过程的优先级；
- 过程标准不规定唯一的生命周期模型或过程顺序；
- 可把现有实践映射到相关过程和任务，以检查完整性并识别 current-to-target gap；
- 记录 defined processes/activities 与生命周期模型的映射、关系和理由，并纳入项目规划；
- 检查所选过程是否有能力实现阶段 outcome。

**FRAMEWORK IMPLICATION**

这为仓库中的 normative gap 方法和 lifecycle/process instantiation record 提供指导性支持，但具体矩阵列、字段、状态与审批规则仍是框架专门化，不能标成标准要求。

### 6.3 适应范围、阶段与 specialty concerns

**GUIDANCE — 6.3**

- 可根据适用性调整过程范围；
- 阶段可合并、删除或增加，但每个保留阶段应有可区分的条件和过程应用；
- specialty concerns 的关键质量特性可以形成额外的阶段退出条件，包括规划、分析和 verification 层级；
- 统一 problem reporting 有利于生命周期管理，可使用 category 和 priority；
- 24748-2:2024 Clause 6 被指为应用 ISO 15288 的系统工程指导来源。

### 6.4 Evaluation activities

**GUIDANCE — 6.4**

标准区分 internal evaluation、verification and validation、joint reviews/audits、quality assurance 和 process improvement。某次生命周期/技术/管理评审是评价与决策机制，不因此成为 Verification Method taxonomy 中的 inspection。

## 7. Clause 7 — 与过程标准的关系

**GUIDANCE — Clause 7**

- ISO/IEC/IEEE 15288 提供通用顶层系统生命周期过程框架；
- 24748-1 为生命周期管理和过程应用提供指导；
- 详细标准或应用标准可扩展通用过程框架；
- 24748-2 为 ISO 15288 的系统工程应用提供进一步指导。

**RESEARCH PRIORITY DECISION**

本研究当时将 ISO/IEC/IEEE 24748-2:2024 设为 `High / Next`；其 targeted review 与随后的 ARP4754B 研究现已完成。当前下一项为 ARP4761A，再进入 item-level assurance standards。该顺序用于先稳定通用骨架和航空系统级边界，不预判后续标准结论。

## 8. 资料性附录

### 8.1 Annex A — Process application

**INFORMATIVE ANNEX**

- 过程可用于任何适用阶段和系统层级；
- 依据风险和成本效益选择用于满足阶段条件的过程；
- 过程可以迭代、递归和并发，排列不表示执行顺序；
- 阶段名称不对应过程组名称；
- 方法和工具不应反向决定过程，工具本身也有生命周期，并需与 system-of-interest 对齐。

### 8.2 Annex C — Project relationships and reviews

**INFORMATIVE ANNEX**

- 项目关系、职责和 enabling systems 需要协调；
- review 应有 initiation、completion 和 documentation criteria。

**FRAMEWORK IMPLICATION**

V6/V12 可以引用这些 review criteria 作为组合对象的一部分，但 review 不能吞并 readiness assessment 或 gate authority。

### 8.3 Annex D — Process views

**INFORMATIVE ANNEX**

Process view 围绕跨生命周期 concern，从 ISO 15288/12207 的多个过程选择并组织活动和任务。它像过程一样可陈述 purpose 和 outcomes，但不定义自己的新活动或任务。一个 view 应说明：

- name；
- stakeholder 与 concern；
- purpose 与 outcomes；
- 实现该 view 的源过程、活动和任务及其引用。

**FRAMEWORK IMPLICATION**

Verification Assurance Process View 必须维护 `view element → source process/activity/task` 映射。框架自己的 gate、记录或 state 可以加入 orchestration layer，但必须标成 interpretation 或 proposal，不能伪装为 ISO task。

### 8.4 Annex E — Development approaches

**INFORMATIVE ANNEX**

- once-through、incremental 和 evolutionary 是可用方式；agile 与 DevOps 可与某些方式关联；
- build planning 应区分各 build、目标、适用活动、reuse 检查、计划决策和进度；
- 活动不必顺序执行，可在多个 build 中并发、持续或间歇发生。

**FRAMEWORK IMPLICATION**

V-ID 是稳定标识而不是执行次序。项目实例需要显式表达 activity invocation、迭代、并行、build/increment 和 re-entry。

### 8.5 Annex F — Technical and management reviews

**INFORMATIVE ANNEX**

- 附录提供候选 joint stakeholder reviews，无意强制采用完整清单，也允许组合或替代；
- review 常为 decision gate 或 milestone 提供信息；
- 候选类别包括计划、运行概念、需求、架构/设计、verification reviews、测试结果、生产准备、部署/运行准备、维护、关键需求以及 change/defect reviews；
- F.3.6 的正式标题是 `Verification reviews`。这些候选评审关注 verification status，包括 test environment、test cases、test procedures，以及被测试 system/element 的状态；其目标还包括评价系统是否已通过 testing、analysis、demonstration 和 inspection 的组合表明满足要求。

**BOUNDARY DECISION**

Annex F 是资料性候选评审集合，F.3.6 不建立强制 `Verification Readiness Review (VRR)`。若框架保留 VRR，必须标为组织/领域惯例或 research proposal，并将其与 Annex F 的通用 `Verification reviews` 分开。

### 8.6 Annex G — Problem reporting

**INFORMATIVE ANNEX**

- 跨生命周期统一 problem reporting 有管理价值；
- category 示例覆盖计划、概念、需求、设计、代码、数据、测试信息、手册等；
- priority 示例考虑能力损失、关键安全/安保影响、workaround、项目或生命周期风险和不便程度；
- 一个 problem 可有多个 category，但有一个 priority。

**BOUNDARY DECISION**

Annex G 不规定通用状态生命周期、tracking/closure workflow 或 disposition authority。框架中的 Problem Report schema、状态机和与 anomaly/change 的关系均需另行定义。

## 12. ISO 15288 与 ISO 24748-1 对照

| Dimension | ISO/IEC/IEEE 15288:2023 | ISO/IEC/IEEE 24748-1:2024 | Framework consequence |
|---|---|---|---|
| Primary role | 系统生命周期过程及 conformance framework | 生命周期管理与过程应用指导 | 将 requirement/task 来源与 guidance 来源分栏 |
| Verification | 定义 Verification Process purpose/outcomes/tasks | 说明过程在阶段、模型和 development approach 中如何应用 | V-architecture 需回链 15288 tasks，并由 24748 指导实例化 |
| Lifecycle model | 不规定单一模型或顺序 | 解释模型、阶段、条件、gates 和非线性关系 | 不把 V0–V12 或六阶段示例做成瀑布流程 |
| Tailoring/adaptation | 提供 conformance tailoring 边界 | 细化语境、标准、阶段、过程映射和理由记录 | 新增受控 instantiation record |
| Process view | 可由跨过程关系理解 | Annex D 提供显式 view 构造指导 | 建立 Verification Assurance Process View 和源任务映射 |
| Reviews | Verification Method 示例中含 inspection/peer review 语境 | Annex F 提供 lifecycle/technical/management review 示例 | 建立双层 review taxonomy |
| Problems | Verification 记录/跟踪 anomaly，并由 supporting processes 处置 | 提供统一 problem reporting 的 category/priority 指导 | 不强行合并 anomaly、problem、change；定义关系 |
| Closure | 支持批准、追溯和 baseline contribution | 支持 stage criteria、gates 和授权 | V12 可获部分指导，但完整 closure state model 仍缺失 |
